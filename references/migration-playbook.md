# 迁移与去重操作手册（SOP）

来自真实机器治理的实战沉淀：27 对副本去重、126 条链接治理、40+ 处路径修复。

## SOP-1 新装技能

1. 真身装进 `~/.agents/skills/<name>/`
2. 需要它的工具目录各建一条软链接：`ln -s ~/.agents/skills/<name> ~/.claude/skills/<name>`
3. 带自引用路径 / venv / API 配置的 → 必做 SOP-3

## SOP-2 迁移 / 中心化（五步）

1. **冲突预检**：中心有无同名
2. **mv 真身 + 原位反向链接**：`mv` 后立刻 `ln -sfn ~/.agents/skills/<name> <原位置>/<name>`，工具视角路径不变、无感知
3. **引用方链接改指**：其他工具目录里指向旧位置的软链接全部 `ln -sfn` 更新
4. **路径体检**（SOP-3）
5. **多端验证**（见 audit-checklist.md）

## SOP-3 路径体检（最易跳过、最易翻车）

`mv` 只搬文件。断点藏在三层，链接层全绿 ≠ 技能可用：

| 层 | 什么会断 | 怎么修 | 怎么验 |
|---|---|---|---|
| 链接层 | 引用方软链指旧位置 | `ln -sfn` 改指 | 逐链接 `[ -e ]` 存在性检查 |
| 内部层 | 脚本/SKILL.md 里的旧绝对路径；venv 的 `bin/activate`（`VIRTUAL_ENV=`）与入口脚本 shebang；`.env` 密钥路径 | `grep -r 旧路径` 逐文件 `sed -i` 重写 | import / `--help` / `--dry-run` 实测 |
| 记忆层 | **其他工具的记忆文件**（如 `~/.codex/memories/`）里存着旧路径，未来会话照记忆调用必错 | 同步 `sed` 修正 | grep 记忆目录 |

实测案例：迁移 6 个技能，链接改完后内部仍查出 40+ 处旧路径（含 venv activate、API 密钥 .env 路径、Codex 记忆文件 8 处）。

## SOP-4 副本合并（diff 分类 → 新者胜）

1. `diff -rq 工具侧 中心` 看差异；结合 SKILL.md 的 mtime 分类
2. **完全一致** → 直接删工具侧实体、原位换软链接
3. **小差异（单文件版本差）** → mtime 新者为真身；工具侧新版先拷入中心再去重
4. **大差异** → `rsync -a --update --exclude '.DS_Store' --exclude '__pycache__'` 双向保新合并；**特别保护 `.env`、`.git`、生成产物目录**
5. 遇到残缺版冒充完整版（一边只有 README、一边结构完整），以完整版为真身，残缺版的独有产物并入

实战数据：27 对副本里挖出路径写错的 bug 版、缺一半文件的残缺版、新版本锁死在单个工具侧。

## 特殊情况

- **工具自管目录（cc-switch 等）**：收编真身后原位留反向软链接，管理器感知不到变化，不会同步回写。注意其设置里可能写着存储位置策略，新装的技能仍会落它自己目录，装完再收编一次。
- **嵌套目录是黑洞**：技能发现只扫一层，`skills/skills/<name>/SKILL.md` 永远不可见。上移一层会"激活"这些技能——先让用户确认要不要激活，不要自作主张上移。
- **工具会重置自己的目录**：升级/卸载可能清空 `~/.<tool>/skills`（实测 35 条链接一夜消失）。真身在中心就不慌，按标准动作重链即可。
- **行为规范型技能**：不提供能力、只改对话风格（如"先澄清再执行"）。真身进中心，链接按需给——链接给谁，谁的性格就变。默认不要全局铺开。
- **同名就近覆盖**：项目级 > 工具本地 > 中心。想给某工具做定制版，在它目录放实体覆盖，中心保持通用。
