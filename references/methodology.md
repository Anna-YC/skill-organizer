# 多智能体技能（Skills）管理方法论
## 单一真身 + 软链接桥接

> 适用场景：同时使用多个 AI 编程智能体（Claude Code、Codex、ZCode、WorkBuddy、CodeBuddy 等），需要让技能（SKILL.md 格式，agentskills.io 开放标准）在多工具间共享、可维护、可验证。

---

## 一、为什么需要方法论：没有它会发生的五件事

1. **各写各的**——每个工具都有自己的技能目录（`~/.claude/skills`、`~/.codex/skills`……），同一个技能装 N 份，存储和管理成本翻倍。
2. **副本漂移**——改了一份忘了另一份，版本悄悄分叉。实战数据：一台真实机器上扫出 **27 对同名副本**，最多的相差 24 处文件，还有"残缺版冒充完整版"、"新版本锁在工具侧没被发现"的情况。
3. **路径断裂**——技能内部写死的绝对路径（脚本调用、venv 虚拟环境、API 密钥文件）在移动后失效。实战数据：迁移 6 个技能后查出 **40+ 处内部断点**。
4. **死链累积**——工具目录里指向已删除/移动位置的软链接越积越多（实测 10 条），技能列表出现"幽灵条目"。
5. **格式统一、位置不统一**——SKILL.md 格式是开放标准，但各工具**发现路径不同**：Claude Code 只认 `~/.claude/skills`，ZCode 原生读 `~/.agents/skills`。格式标准解决不了存放问题。

## 二、核心架构：一个中心、两种目录、四类技能

**总原则：真身唯一，引用用链接（Single Source of Truth + Symlink Bridging）。**

```
~/.agents/skills/              ← 中心仓库：所有跨工具技能的唯一真身
   ├── skill-A/                ← 实体文件
   └── skill-B/

~/.claude/skills/              ← 各工具目录：只放软链接 + 工具专属技能
   ├── skill-A -> ~/.agents/skills/skill-A
   └── tool-only-X/            ← 专属技能例外

~/.agents/skills.disabled/     ← 停用区：挪进去即全局停用
~/.agents/skills-backups/      ← 备份区：升级前存旧版
```

### 四类技能的安置规则（分类安置）

| 类型 | 判别标准 | 安置位置 |
|---|---|---|
| **能力型跨工具技能** | 提供新能力、≥2 个工具要用（生图、转写、PPT） | 真身进中心，各工具链接 |
| **工具专属技能** | 只有一个工具用（如剪映 API 只给 Codex） | 留在工具自己的目录 |
| **行为规范型技能** | 不提供新能力，而是改变对话风格（如"先澄清意图再执行"） | 真身进中心，**按需链接**——链接给谁，谁的性格就变 |
| **项目级技能** | 只在某个仓库里有意义 | 放项目目录，不进用户级中心 |

> ⚠️ 第三类最容易被忽略：全局激活一个行为型技能 = 同时改变所有工具的对话风格（简单任务可能被多余反问拖慢）。正确姿势是真身进中心、链接按需给，想给哪个工具启用就补一条链接。

### 就近覆盖（Local Override）

同名技能时，工具本地目录的发现优先级**高于**中心（如 ZCode：项目级 > `~/.zcode/skills` > `~/.agents/skills`）。想对某个工具单独定制某个共享技能，就在它的目录里放一份实体覆盖——中心版本保持通用，本地版本做特化。

## 三、标准作业程序（SOP）

### SOP-1 新装技能（三步）
1. 真身装进 `~/.agents/skills/<name>/`
2. 需要它的工具目录各建一条软链接
3. 若带自引用路径 / venv / API 配置 → 必须做 SOP-3 路径体检

### SOP-2 迁移 / 中心化（五步）
1. 冲突预检：中心有无同名
2. `mv` 真身 + 原位**反向**软链接（工具视角路径不变，无感知）
3. 引用方链接改指新位置
4. 路径体检（SOP-3）
5. 多端验证（第五节清单）

### SOP-3 路径体检（最易跳过、最易翻车）
- `grep -r 旧路径` 扫技能全部文件（SKILL.md、脚本、元数据）
- venv 技能：重写 `activate` 脚本的 `VIRTUAL_ENV` 和入口脚本 shebang 里的绝对路径
- API 密钥注册表（.env）：确认脚本 `expanduser` 后能解析到新路径
- **其他工具的记忆文件**（如 Codex memories）里引用的旧路径同步修正——记忆会指导未来会话用错路径
- 运行时实测：`--help` / `--dry-run` / `import`
- 关键认知：**链接层全绿 ≠ 技能可用**，软链接机制暴露不了内部断点

### SOP-4 副本合并（diff 分类 → 新者胜）
1. `diff -rq` 找差异，按"独有文件数 + SKILL.md 修改时间"分类
2. 完全一致 → 直接删工具侧换链接
3. 小差异 → mtime 新者为真身
4. 大差异 → `rsync -a --update` 合并（双向保新、保留双方独有文件），特别保护 `.env`、`.git`、生成产物等工具侧资产
5. 排除 `__pycache__`、`.DS_Store` 等垃圾

## 四、五层验收清单

| 层 | 验什么 | 方法 |
|---|---|---|
| 1 链接层 | 所有工具目录零断链 | 逐链接 `-e` 存在性检查 |
| 2 发现层 | 模拟每个 Agent 视角，技能全部可发现 | 逐条目验证 SKILL.md 可达 |
| 3 内容层 | 旧路径零残留 | grep 全目录（排除历史会话日志） |
| 4 功能层 | 关键技能真的能跑 | dry-run 实测凭据/依赖/产物 |
| 5 盲点层 | 记忆文件、云同步、商店元数据、清单文件 | 逐机制扫描 |

## 五、六条经验教训（实战背书）

1. **mv ≠ 迁移完成**。链接修好只通了第一层；技能内部路径、venv、密钥引用是第二层；其他 Agent 的记忆文件是第三层。
2. **副本不是无害的**。实战 27 对副本里挖出：写错路径的 bug、残缺版顶替完整版、新版本锁死在单工具侧。
3. **分清能力型与行为型**。能力型全局共享是红利；行为型全局激活是风格突变，要按需分配。
4. **工具自管目录要留反向链接**。cc-switch 这类管理工具自己维护技能库，收编真身后原位留软链接，工具视角不变，避免同步回写冲突。
5. **嵌套目录是黑洞**。发现机制只扫一层，`skills/skills/` 里的技能任何工具都看不见（实测 6 个技能被困 234MB）。
6. **工具会重建自己的目录**。升级/卸载可能重置技能目录（CodeBuddy 实测），桥接链接要按标准动作重建。

## 六、一页总结

> **真身唯一 · 链接桥接 · 分类安置 · 就近覆盖 · 迁移体检 · 五层验收**

- 中心放真身，工具放链接，改一处、多端生效
- 能力型共享、行为型按需、专属留原地、项目随仓走
- 每次迁移必做路径体检 + 运行实测
- 定期跑五层验收，副本和死链不留过夜
